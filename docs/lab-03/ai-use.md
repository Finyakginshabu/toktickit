## Reflection

In this lab, I switched from Gemini 3.7 (Medium) to Gemini 3.8 (High) because the medium thinking model's implementations sometimes failed to meet the criteria, repeatedly failed tests, and got stuck in fix loops. Although this switch consumed significantly more tokens, it delivered far better results.

The strict separation between planning, contract drafting, and execution proved critical. Forcing the agent to inspect reference documents and generate comprehensive engineering contracts before writing a single line of code prevented scope creep and eliminated guesswork. When architectural conflicts arose, forcing explicit decision gates (such as choosing authentication mechanisms and data models) guaranteed complete alignment with lab requirements.

Decomposing the contracts into granular GitHub issues created clear boundaries for implementation, complete with acceptance criteria, test suites, and traceability back to business requirements. Having the agent create an implementation plan first for every issue, execute the changes, and conduct a post-implementation review against docs/issues/x.md ensured high code quality and smooth pull requests. This contract-first, step-by-step approach made complex multi-file changes manageable, completely transparent, and verifiable.
